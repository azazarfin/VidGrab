## ADR-001 — Desktop companion with a reusable Python engine

- **Date:** 2026-11-03. **Status:** product direction confirmed; stack accepted for the selected Linux/Windows P02 preview baselines on 2026-11-10.
- **Decision:** build a standalone download/settings app that also serves the extension. Use Tauri 2 + TypeScript/React, a small Rust owner/bridge and a packaged Python engine; P02 accepts this stack for the tested preview baselines.
- **Why:** reuse yt-dlp/Python behavior and web UI skills while moving lifecycle/installation behind one app. Python workers provide enforceable isolation; shared contracts avoid a second business-logic implementation.
- **Tradeoff:** Rust, Python, and a web frontend add build complexity; Tauri depends on OS webviews. Evaluate real installers before investing in UI. PySide6 is the fallback if Tauri packaging/integration is disproportionately complex; Electron would simplify the web runtime but add distribution weight. A full Rust downloader rewrite discards useful Python integration.
- **Gate:** clean Linux/Windows installation, no external language runtime, functioning tray/fallback window and browser-to-app activation. Record measured size/startup results before accepting the stack.
- **Linux review — 2026-11-10:** the selected Ubuntu 24.04/GNOME x86_64 preview passes installation/removal, bundled runtime/tools, tray/fallback, lifecycle and native Chrome/Firefox activation. Strict Snap and guided Flatpak portal setup have separate passing evidence. Final `.deb` is 129.37 MiB and AppImage 193.51 MiB; three fresh-state registered launches yield medians 0.854 s and 1.478 s, including WebDriver launch/session and observation overhead but excluding registration/driver preparation. See [the acceptance review](VALIDATION.md#p02-final-ubuntu-startup-and-linux-acceptance-review--2026-11-10) for ranges and limits.
- **Windows review — 2026-11-10:** the exact current-user NSIS passes fresh GUI installation/removal/reinstall, trusted receipt/refusal/privacy checks, spaces/Bangla, actual Chrome/Firefox, tray/fallback, owned cleanup and bundled tool/native dependencies. With real SDK discovery unavailable through reversible machine-key masking, the bundled offline installer supplies a per-user WebView2 runtime without elevation and the app renders through it. The machine runtime files remain; physical absence/Windows 10 is not claimed. Installer 301.96 MiB; 89 installed files 308.88 MiB; three fresh explicit application runtimes with existing selected WebView/warm OS caches yield median 1.225 s (1.179–1.789 s), including task/CDP/observation overhead. See [the scoped Windows review](VALIDATION.md#p02-windows-webview2-startup-and-final-acceptance--2026-11-10).
- **Engineering conclusion:** accept Tauri/React, Rust owner/bridge and frozen Python for P02 on the selected Ubuntu 24.04/GNOME x86_64 and Windows 11 x64 baselines. The package/build/lifecycle evidence supports this integration cost; the PySide6 fallback is unnecessary for this feasibility scope. P03 has not started. P07 repeats release acceptance, including advertised minimum OS versions, genuinely clean prerequisite baselines, signing/update/recovery and release budgets; additional Linux configurations and physical hardware remain separate claims.

## ADR-003 — App-owned lifecycle and native messaging first

- **Date:** 2026-11-03. **Status:** proposed, P02/P04 gates.
- **Decision:** app supervisor owns the engine and workers; browser native host is a replaceable bridge. Use app-owned per-user IPC plus authenticated internal loopback API. Evaluate an explicitly paired loopback extension fallback for sandboxed installations.
- **Why:** browser closure/service-worker suspension must not terminate jobs. Native messaging provides browser registration and app activation without asking users to start a backend or enter a port.
- **Tradeoff:** host registration and browser-specific process lifetime need installer support. A plain unauthenticated localhost server is not the production fallback. Background operation remains visible and controllable in the app.

## ADR-004 — Layered compatibility and bounded retries

- **Date:** 2026-11-03. **Status:** proposed reliability policy, P03/P05 gates.
- **Decision:** extractor-first, then direct-media/manifest detection with shared browser context. Use one bounded request/retry policy and typed failure states; benchmark against explicit fixtures and a live-site matrix.

## ADR-016 — Durable attempt identities and retained publication records

- **Date:** 2026-11-14. **Status:** attempt/artifact bookkeeping implemented; P03 remains in progress and is not accepted.
- **Decision:** schema 3 commits each queued-job claim with a numbered UUID attempt. Terminal transitions and progress use that attempt ID; one running-attempt index prevents duplicate claims. Keep literal artifact paths in a related table, with history deletion cascading metadata while retaining files. Transactional upgrades from 0/1/2 preserve historical rows without inventing attempts.
- **Ownership/publication:** exclusively create `data_dir/attempts/<UUID>`, stage yt-dlp outputs there, and capture concrete post-processing moves. Fsync bounded planned/completed journal records before publication/result respectively. Refuse existing destinations and unsafe workspace/journal links or reparse points. Do not guess extensions, scan media by filename prefix or delete unrelated files.
- **Failure semantics:** joined worker-tree exit precedes cookie cleanup, retained-file scanning and terminal persistence. Recovery retains partial/published records; an incomplete final journal line is tolerated. Invalid journals fail the executing attempt while preserving files. Existing destinations may require a different filename on retry until publication reconciliation is implemented.
- **Unfinished boundary:** ADR-017 adds owner identity/lease fencing and gated service kill/restart; ADR-018 now implements verified publication reconciliation. ADR-019 adds durable cookie ownership and crash cleanup; resume stays disabled. Verified resume, playlists/idempotency and persisted retry/request budgets remain separate work. Journal fsync is not a power-loss acceptance claim.
- **Evidence:** guarded migration/claim/terminal/recovery/ownership tests, real staged media/subtitle/thumbnail checks and source/frozen worker/native compatibility are scoped in [VALIDATION.md](VALIDATION.md) and [HANDOFF](../HANDOFF.md#p03-durable-attempts-and-artifacts-checkpoint--2026-11-14). Current Windows worker/junction runs use elevated Azaz, adding no new standard-user/GUI/installer claim.

## ADR-017 — Durable runtime ownership and recovery fencing

- **Date:** 2026-11-14. **Status:** implemented and verified for the selected Linux/Windows source and frozen boundaries; P03 remains in progress and unaccepted.
- **Decision:** schema 4 persists runtime/attempt ownership, leases and worker identities. Every engine lifespan holds a separate file lock before database initialization, including legacy ASGI and diagnostics. Identity uses Linux creation ticks/boot/hashed machine ID or Windows creation FILETIME/hashed MachineGuid. Unknown/inaccessible identity refuses recovery. Lease expiry never authorizes takeover of a live process; confirmed death permits retirement before expiry. Leases renew every 10 seconds for 30 seconds.
- **Startup barrier:** commit the worker owner and waiting worker identities transactionally before bootstrap delivery. Validate active runtime/attempt/current-job ownership; a launch retired by recovery cannot execute. Recovery checks every owner/tree before artifact reads or state changes, including surviving Linux session/group members after leader exit. Claims/terminal writes validate durable ownership alongside attempt/state fencing.
- **Lifecycle/migration:** retain the non-inheritable lock through joined execution and never unlink it on normal release. Renewal failure marks readiness false and joins workers. Startup cancellation joins committed acquisition; failed cleanup retains unreleased metadata. Upgrades from 0–3 preserve history; schema-3 running attempts without identity are quarantined by recovery refusal rather than assigned invented owners. Pre-attempt legacy compatibility requires old services to be stopped before migration.
- **Evidence/limits:** 157 guarded cases, source/frozen service overlap/kill/restart/launch-retirement checks, Linux orphan-owner/group refusal, Windows Job Object/protocol/media/native compatibility and six junction cases pass. Windows tests use elevated Azaz; Ubuntu userspace shares Fedora's kernel. Gated restart preserves prior partials in a new attempt; complete publication/cookie crash recovery, verified resume and power-loss durability remain separate gates. See [VALIDATION.md](VALIDATION.md#p03-owner-fencing-and-service-restart-checks--2026-11-14) and [HANDOFF](../HANDOFF.md#p03-durable-owner-and-lease-checkpoint--2026-11-14).

## ADR-018 — Verified publication and crash reconciliation

- **Date:** 2026-11-14. **Status:** implemented and verified for the selected Linux/Windows source and frozen boundaries; P03 remains in progress and unaccepted.
- **Decision:** retain unshared staged-file witnesses with device/inode identities, SHA-256 digests and destination-directory identities in version-2 artifact journals. Fsync ready records before final hard-link creation without replacement. Cross-volume publication first creates/copies an exclusive destination-volume witness, records its ownership and verifies the copy before linking. Filesystems lacking verifiable identities or link support fail while retaining files. Keep literal paths and existing filename policy.
- **Recovery:** record a durable result footer matching the complete artifact set. After all runtime/worker fences pass, a verified footer and owned outputs restore completion within the same attempt. Unpublished work may requeue; partial, missing, changed, foreign or unverifiable publication fails without automatic retry and preserves files. Persisted cancellation wins. Legacy journals cannot adopt existing destinations; repeated recovery leaves completed history untouched.
- **Cleanup/cancellation:** retain witnesses until SQLite commits success. Join startup verification before rollback and terminal verification/postcommit cleanup through repeated caller cancellation. Cleanup rechecks ownership/content and removes only verified witnesses, preserving unrelated or changed files. ADR-019 adds the separate durable cookie-file ownership and crash-cleanup boundary.
- **Windows containment:** actual venv redirectors could create an interpreter before Job Object assignment. Launch the private owner detached and the worker detached/suspended, assign the non-inheritable kill-on-close Job Object, then resume the unique, kernel-verified primary thread through supported Win32 APIs. Keep explicit pipe/handle whitelists; startup failure joins the process/tree and closes its owned pipes.
- **Evidence/limits:** 184 guarded cases pass on Fedora, Ubuntu userspace and Windows, plus source/fresh frozen protocol, ten real-media including cross-volume, eight Linux/six Windows service, eleven Linux/six Windows native and nine Windows junction cases. Before/after-link service publishers are synthetic; the result-before-SQLite check uses a real WAV→MP3 worker. Windows checks use elevated Azaz and Ubuntu userspace shares Fedora's kernel; no new standard-user/GUI/installer baseline is claimed. Power-loss durability, arbitrary concurrent parent-directory mutation, verified resume and remaining P03 budgets/jobs are unaccepted. See [VALIDATION](VALIDATION.md#p03-publication-reconciliation-checks--2026-11-14) and [HANDOFF](../HANDOFF.md#p03-publication-reconciliation-checkpoint--2026-11-14).

## ADR-019 — Durable cookie ownership and crash cleanup

- **Date:** 2026-11-14. **Status:** implemented and source/fresh frozen checks pass on Fedora, Ubuntu userspace and Windows 11. P03 remains in progress and unaccepted.
- **Decision:** schema 5 adds bounded non-secret `attempt_cookie_files` records, linked to their durable attempts. Cookie contents stay outside SQLite/download options. Reserve two empty names in an exclusive UUID directory under the attempt's `.vidgrab` tree, retain their file and directory identities, and commit ownership with `synchronous=FULL` before writing any cookie bytes. Flush/fsync the Netscape file before marking delivery ready. The literal path must match the ready record at the worker's transactional bootstrap barrier.
- **Mutable jar:** retain a private hard-link witness because yt-dlp rewrites its cookie jar on close. Both names must identify the recorded inode with exactly two known links. A cleanup interrupted after removing the primary name may remove the verified remaining witness with one link; both absent names permit clearing the record. Preserve foreign/replaced names, additional hardlinks, symbolic links and reparse points. Validate canonical attempt UUIDs and all recorded directories before opening a file. Never adopt or delete leftovers by a filename prefix.
- **Privacy:** Linux credential directories/files use 0700/0600. Windows protects the new directory's DACL before creating files, granting inherited access only to the current account and SYSTEM. Netscape fields reject row separators, invalid expirations and oversized input. Forwarded input is limited to 1 MiB/4,096 cookies; ownership records to 8 KiB. Diagnostic messages exclude cookie values.
- **Lifecycle:** creation threads, execution and cleanup remain joined through repeated cancellation. Every startup fences all running attempts and pending cookie records, including terminal attempts, before any recovery file reads or resets. Active/live or unverifiable owners/workers refuse recovery; a safely released terminal owner requires the current runtime lock and verified worker exit. Clear the ownership row only after verified file removal. Unverifiable cleanup preserves files/metadata and stops automatic retry; persisted cancellation wins. History deletion retains jobs with pending cookie ownership.
- **Crash scope:** opt-in checks instrument an owned source app at empty reservation, committed ownership, partial/full writing, ready delivery and before/between/after cleanup unlinks. They use real loopback media for delivered/completed attempts. Frozen checks use frozen workers and the entire frozen service for restart/reconciliation; the creation producer remains source instrumentation. These checks do not establish power-loss durability, arbitrary concurrent parent mutation, secure erasure or new standard-user/GUI/installer acceptance. Empty unregistered files and old unowned temp files remain preserved.
- **Next:** verified partial resume with source validators and fresh browser authentication, then playlists/idempotency and persisted retry/request budgets. The recovered jar is discarded, never reused. `waiting_for_auth` and the full auth-refresh flow remain later work; `/v1` remains P04. Evidence belongs with [the current checkpoint](../HANDOFF.md#p03-cookie-ownership-and-crash-recovery-checkpoint--2026-11-14).
